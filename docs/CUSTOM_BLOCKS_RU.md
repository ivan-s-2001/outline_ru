# Разработка собственных блоков Outline

Это руководство описывает правила разработки новых блоков редактора в исходном коде Outline. Речь идёт не о пользовательском конструкторе в интерфейсе: новый блок является частью приложения и после добавления требует пересборки.

В этом форке предусмотрены две отдельные точки расширения:

```text
shared/editor/nodes/custom/index.ts   — регистрация узлов редактора
app/editor/menus/custom.tsx           — регистрация пунктов меню `/`
```

Они позволяют хранить свои блоки отдельно от основного списка Outline и уменьшают конфликты при обновлении исходного проекта.

## Из чего состоит блок

Полноценный блок обычно включает:

| Часть | Назначение |
| --- | --- |
| Node-класс | схема ProseMirror, атрибуты, допустимое содержимое |
| HTML-сериализация | `parseDOM` и `toDOM` |
| Markdown-сериализация | `toMarkdown`, `parseMarkdown`, при необходимости markdown-it rule |
| Команды | вставка, удаление, изменение атрибутов |
| React-представление | интерактивный интерфейс сложного блока |
| Пункт slash-меню | вставка блока через `/` |
| Локализация | подписи, подсказки и сообщения |
| Тесты | импорт, экспорт, команды, обратная совместимость |

## Основные типы блоков

### 1. Обычный блочный узел

Подходит для блока, который можно полностью описать через DOM.

Примеры в Outline:

```text
shared/editor/nodes/Blockquote.ts
shared/editor/nodes/HorizontalRule.ts
shared/editor/nodes/Notice.tsx
```

Базовый класс:

```ts
import Node from "../Node";
```

### 2. Контейнерный блок

Содержит другие узлы: абзацы, заголовки, списки, код.

Примеры:

```text
shared/editor/nodes/Notice.tsx
shared/editor/nodes/ToggleBlock.tsx
```

Для контейнера задаётся `content`, например:

```ts
content: "block+"
```

или более строго:

```ts
content: "(paragraph | heading | list | blockquote)+"
```

Контейнеры рекомендуется называть с префиксом `container_`.

### 3. Атомарный React-блок

Используется для виджетов, вложений, внешних данных, карточек и другого интерфейса, внутри которого нет обычного редактируемого текста ProseMirror.

Примеры:

```text
shared/editor/nodes/Attachment.tsx
shared/editor/nodes/Embed.tsx
shared/editor/nodes/Image.tsx
```

Типичная схема:

```ts
atom: true,
selectable: true,
defining: true,
group: "block",
```

Интерфейс рендерится через метод `component` и получает `ComponentProps`.

## Рекомендуемая структура

```text
shared/editor/
├── nodes/
│   └── custom/
│       ├── index.ts
│       ├── StatusCard.tsx
│       └── CustomPanel.tsx
├── components/
│   └── custom/
│       ├── StatusCardView.tsx
│       └── CustomPanelView.tsx
└── rules/
    └── customPanel.ts

app/editor/menus/custom.tsx
```

Простой блок можно держать в одном файле. React-компонент стоит выносить отдельно, когда он становится крупным, содержит несколько состояний или переиспользуется.

## Именование

### Имя узла

```ts
get name() {
  return "container_custom_panel";
}
```

Правила:

- только латиница и `snake_case`;
- имя должно быть уникальным во всей схеме редактора;
- контейнеры — `container_*`;
- атомарные блоки — существительное: `status_card`, `calendar`, `ticket`;
- после появления блока в документах имя нельзя менять без миграции;
- имя команды вставки желательно делать равным имени узла.

### CSS-классы

Используйте отдельный стабильный корневой класс:

```html
<div class="custom-panel">...</div>
```

Внутренние элементы оформляйте по BEM-подобной схеме:

```text
custom-panel
custom-panel__header
custom-panel__content
custom-panel__actions
custom-panel--warning
```

Не используйте общие имена вроде `.content`, `.header`, `.title` без привязки к корню блока.

## Атрибуты узла

Атрибуты — это данные документа, которые сохраняются и передаются при совместном редактировании.

Хороший пример:

```ts
attrs: {
  title: { default: "" },
  tone: { default: "neutral" },
  collapsed: { default: false },
  sourceId: { default: null },
}
```

Не храните в атрибутах:

- hover-состояние;
- открытое меню;
- временную загрузку;
- React-компоненты;
- функции;
- токены доступа;
- права пользователя;
- большие ответы внешнего API.

Правила:

1. Все значения должны быть JSON-сериализуемыми.
2. У необязательных атрибутов должен быть `default`.
3. Значения с ограниченным набором вариантов должны проверяться.
4. URL должны проходить через существующие функции очистки.
5. Данные документа нельзя хранить только в локальном React-state.
6. Изменения атрибутов выполняются транзакциями ProseMirror.

## Схема блока

Минимальный контейнерный блок:

```ts
import type { NodeSpec, NodeType } from "prosemirror-model";
import type { Primitive } from "utility-types";
import toggleWrap from "../../commands/toggleWrap";
import Node from "../Node";

export default class CustomPanel extends Node {
  get name() {
    return "container_custom_panel";
  }

  get schema(): NodeSpec {
    return {
      attrs: {
        tone: { default: "neutral" },
      },
      content: "block+",
      group: "block",
      defining: true,
      draggable: true,
      parseDOM: [
        {
          tag: "div.custom-panel",
          contentElement: ".custom-panel__content",
          getAttrs: (dom: HTMLDivElement) => ({
            tone: dom.dataset.tone || "neutral",
          }),
        },
      ],
      toDOM: (node) => [
        "div",
        {
          class: `custom-panel custom-panel--${node.attrs.tone}`,
          "data-tone": node.attrs.tone,
        },
        ["div", { class: "custom-panel__content" }, 0],
      ],
    };
  }

  commands({ type }: { type: NodeType }) {
    return {
      container_custom_panel: (attrs: Record<string, Primitive>) =>
        toggleWrap(type, attrs),
    };
  }
}
```

Число `0` в `toDOM` обозначает место дочернего содержимого ProseMirror.

## HTML: чтение и запись

Каждый блок обязан поддерживать оба направления:

```text
ProseMirror → HTML
HTML → ProseMirror
```

Для этого используются:

```ts
parseDOM: [/* правила чтения */]
toDOM: (node) => [/* DOMOutputSpec */]
```

Принципы:

- корневой тег должен быть стабильным;
- данные хранятся в `data-*`, а не извлекаются из визуального текста;
- `parseDOM` должен безопасно обрабатывать отсутствие атрибутов;
- при изменении HTML новая версия должна продолжать читать старую разметку;
- пользовательский текст нельзя вставлять в HTML небезопасным способом;
- внешние URL необходимо очищать.

## Markdown: импорт и экспорт

Базовый класс `Node` требует реализации `toMarkdown`. Без этого экспорт документа завершится ошибкой.

Для контейнера удобно использовать fenced-синтаксис:

```md
:::custom-panel warning
Содержимое блока
:::
```

Обычно нужны:

```ts
get rulePlugins() {
  return [customPanelRule];
}

toMarkdown(state, node) {
  // запись Markdown
}

parseMarkdown() {
  // сопоставление markdown-токена с узлом
}
```

В качестве рабочего образца используйте:

```text
shared/editor/nodes/Notice.tsx
shared/editor/rules/notices.ts
```

Обязательное требование:

```text
редактор → Markdown → редактор
```

не должно терять содержимое и значимые атрибуты блока.

Если блок невозможно полноценно представить стандартным Markdown, используйте устойчивый расширенный синтаксис и предусмотрите понятный fallback для сторонних редакторов.

## Команды

Команда отвечает за изменение документа.

Основные правила ProseMirror:

- команда возвращает `true`, если применима;
- команда возвращает `false`, если её нельзя выполнить;
- без `dispatch` команда только проверяет применимость и не меняет документ;
- все изменения выполняются через `state.tr`;
- после вставки нужно корректно установить selection;
- команда должна поддерживать undo/redo;
- нельзя напрямую изменять `node.attrs`.

Изменение атрибутов существующего узла:

```ts
const transaction = state.tr.setNodeMarkup(position, undefined, {
  ...node.attrs,
  tone: "warning",
});

dispatch?.(transaction);
```

Для контейнеров можно использовать существующий `toggleWrap`. Для атомарных блоков обычно создаётся узел через `type.create(...)` и вставляется транзакцией.

## React-представление

Сложный блок может объявить:

```ts
component = (props: ComponentProps) => {
  // React-представление
};
```

Наиболее важные свойства:

- `node` — текущий ProseMirror-узел;
- `getPos()` — позиция узла в документе;
- `isSelected` — выбран ли блок;
- `isEditable` — доступно ли редактирование;
- `theme` — текущая тема;
- `view` доступен через `this.editor.view`.

Правила:

1. Данные документа берутся из `node.attrs`.
2. Изменения документа выполняются командой или транзакцией.
3. Локальный state используется только для временного UI.
4. В read-only режиме элементы управления скрываются или блокируются.
5. События внутри интерактивного блока не должны случайно перемещать курсор редактора.
6. Выбранный блок должен иметь видимое состояние selection.
7. Ошибка внешнего API не должна ломать весь документ.

## Оформление блока

### Цвета

Не используйте фиксированные цвета интерфейса:

```css
color: #000;
background: #fff;
```

Используйте токены темы и существующие helpers Outline. Блок обязательно проверяется в светлой и тёмной темах.

Исключение — смысловые пользовательские цвета, которые являются данными документа. Для них всё равно нужен контрастный текст и корректное отображение в обеих темах.

### Размеры

- ширина блока по умолчанию не должна превышать ширину документа;
- избегайте фиксированной высоты;
- длинный текст должен переноситься;
- таблицы и код могут использовать горизонтальный скролл;
- блок должен работать на мобильной ширине;
- изменение selection не должно менять размеры и сдвигать документ.

### Отступы

Используйте визуальный ритм существующих блоков Outline:

- небольшие внутренние отступы у компактных карточек;
- увеличенные отступы у контейнеров с содержимым;
- одинаковое расстояние между заголовком, телом и действиями;
- без дополнительных внешних `margin`, если расстояние уже управляется редактором.

### Состояния

Продумайте:

- обычное состояние;
- hover;
- focus-visible;
- selection;
- disabled;
- read-only;
- loading;
- error;
- пустое состояние.

Цвет не должен быть единственным способом обозначения состояния.

## Slash-меню

Пункты собственных блоков добавляются только в:

```text
app/editor/menus/custom.tsx
```

Пример:

```tsx
import type { TFunction } from "i18next";
import { InfoIcon } from "outline-icons";
import type { RefObject } from "react";
import type { MenuItem } from "@shared/editor/types";

export default function customBlockMenuItems(
  t: TFunction,
  _documentRef: RefObject<HTMLDivElement>
): MenuItem[] {
  return [
    { name: "separator" },
    {
      name: "container_custom_panel",
      title: t("Custom panel"),
      keywords: "panel card custom",
      icon: <InfoIcon />,
      attrs: { tone: "neutral" },
    },
  ];
}
```

Требования:

- `name` совпадает с командой узла;
- `title` локализован;
- `keywords` содержат английские и при необходимости русские варианты поиска;
- иконка берётся из `outline-icons` или соответствует визуальному стилю существующих иконок;
- одинаковые блоки с разными начальными атрибутами можно показывать отдельными пунктами.

## Регистрация узла

Добавьте класс в:

```text
shared/editor/nodes/custom/index.ts
```

```ts
import type { AnyExtensionClass } from "../../lib/types";
import CustomPanel from "./CustomPanel";

export const customBlockExtensions: AnyExtensionClass[] = [CustomPanel];
```

Порядок имеет значение:

1. простые атомарные блоки;
2. обычные блочные узлы;
3. контейнерные узлы.

Не добавляйте новый класс напрямую в основной массив `richExtensions`, если это блок данного форка.

## Локализация

Строки интерфейса пишутся через i18next:

```tsx
t("Custom panel")
```

или:

```tsx
<Trans>Custom panel</Trans>
```

Правила:

- ключи пишутся на английском;
- русский текст не используется как ключ;
- новая строка добавляется минимум в `en_US` и `ru_RU`;
- пользовательское содержимое не переводится;
- enum и внутренние значения атрибутов остаются языконезависимыми.

## Доступность

Интерактивный блок должен поддерживать:

- клавиатурную навигацию;
- `focus-visible`;
- `aria-label` у кнопок без текста;
- семантические `button`, `a`, `input`;
- достаточный контраст;
- действия, доступные не только по hover;
- корректный порядок tab-навигации;
- понятные сообщения об ошибках.

Не превращайте обычный `div` в кнопку без роли, tabIndex и клавиатурной обработки.

## Работа с внешними данными

Если блок обращается к API:

- не храните секреты в документе;
- запросы должны проходить через сервер, когда требуется авторизация;
- используйте стабильный ID ресурса, а не весь ответ API;
- предусматривайте timeout, loading, error и retry;
- не делайте сетевой запрос на каждый рендер;
- учитывайте SSR и отсутствие `document` на сервере;
- не позволяйте внешнему HTML выполняться внутри документа;
- для удалённого контента должен быть текстовый fallback.

## Обратная совместимость

После использования блока в рабочих документах его схема становится частью формата данных.

Нельзя без миграции:

- менять `name`;
- удалять обязательный атрибут;
- менять тип значения атрибута;
- удалять поддержку старого HTML;
- менять Markdown-синтаксис без чтения старой версии;
- удалять узел из схемы редактора.

Безопасное изменение:

1. добавить новый необязательный атрибут с `default`;
2. научить `parseDOM` читать старый и новый HTML;
3. записывать только новый HTML;
4. оставить чтение старого Markdown;
5. при необходимости выполнить миграцию документов.

## Тестирование

Минимальный набор проверок:

### Схема

- узел создаётся с минимальными атрибутами;
- default-значения применяются;
- недопустимое содержимое отвергается.

### HTML

- `toDOM` создаёт ожидаемую разметку;
- `parseDOM` восстанавливает узел;
- старый HTML продолжает импортироваться.

### Markdown

- экспорт формирует ожидаемый текст;
- импорт восстанавливает атрибуты;
- round-trip не теряет данные.

### Команды

- вставка работает в допустимой позиции;
- команда возвращает `false` в недопустимой позиции;
- изменение атрибутов поддерживает undo/redo;
- удаление не повреждает соседние блоки.

### Интерфейс

- edit и read-only;
- светлая и тёмная темы;
- мобильная ширина;
- клавиатура;
- selection;
- loading и error;
- совместное редактирование двумя клиентами.

## Порядок разработки нового блока

1. Найдите ближайший стандартный блок-образец.
2. Определите, является блок контейнерным или атомарным.
3. Зафиксируйте имя узла и Markdown-формат.
4. Создайте файл в `shared/editor/nodes/custom`.
5. Опишите `attrs`, `content`, `group`, `parseDOM`, `toDOM`.
6. Реализуйте Markdown-импорт и экспорт.
7. Реализуйте команды.
8. Добавьте React-представление, если оно нужно.
9. Зарегистрируйте узел в `customBlockExtensions`.
10. Добавьте пункт в `customBlockMenuItems`.
11. Добавьте локализацию.
12. Добавьте тесты.
13. Проверьте экспорт, импорт и старые документы.
14. Пересоберите приложение или Docker-образ.
